▸ 2026-10-02T03:52:05Z [Joel Webber]
Root cause found: **/etc/pam.d/greetd has no pam_gnome_keyring.so at all**, so
nothing ever hands your login password to the keyring daemon. The dialog is
gcr-prompter asking for the password PAM should have supplied.

Evidence:

- The display manager is **greetd** (`greetd.service` active, running
  `/usr/bin/noctalia-greeter-session`). `sddm` is installed but idle.
- `grep -rn gnome_keyring /etc/pam.d/` matches **only /etc/pam.d/sddm** and
  /etc/pam.d/sddm-autologin -- the vendor files for the DM that is *not* in
  use. Those are why the setup looks correct at a glance.
- /etc/pam.d/greetd in full: pam_securetty, pam_nologin,
  `include system-local-login` x3, `session required pam_systemd.so`. No
  keyring module anywhere, and the include chain
  (system-local-login -> system-login -> system-auth) has none either.
- noctalia-greeter *did* run its own PAM patcher -- there is a
  `/etc/pam.d/greetd.bak.noctalia.20260913165958` backup -- but
  /usr/share/noctalia-greeter/setup_greetd_pam.sh only ever inserts
  pam_systemd.so. It has no notion of keyrings. So the file looks
  "already configured" while missing the thing we need.
- The daemon is running twice: PID 1294 `--start --components=secrets` and
  PID 1309 `--components=pkcs11,secrets --control-directory=...`, both
  parented to the user systemd manager (1160). Started by
  gnome-keyring-daemon.service/.socket plus /etc/xdg/autostart/*.desktop --
  i.e. started *outside* PAM, which is exactly why it has no password to
  unlock with.
- Journal, boot 0: gcr-prompter[1323] prompts at 22:13:17, 4s after login,
  then `10 second inactivity timeout, quitting`. Afterwards a steady trickle of
  `asked to register item /org/freedesktop/secrets/collection/login/9, but
  it's already registered` as apps re-request secrets.

Fix: add two lines to /etc/pam.d/greetd. Full proposed file:
![greetd.pam](artifacts/dots-2998/greetd.pam)

    sudo cp /etc/pam.d/greetd /etc/pam.d/greetd.bak.keyring
    sudo install -m 0644 .yaks/artifacts/dots-2998/greetd.pam /etc/pam.d/greetd

Takes effect on next login, not reload. Keep the backup and a TTY handy: a
broken /etc/pam.d/greetd locks you out of the graphical login.

Two caveats worth knowing before blaming the fix:

1. The unlock only works if the **login keyring password equals the login
   password**. ~/.local/share/keyrings/login.keyring exists (2.8K, mtime
   2026-10-01 23:42). If the prompt persists after this change, that is the
   reason -- re-set the keyring password to match in seahorse, or delete
   login.keyring and let it be recreated at next login (you lose stored
   secrets).
2. `auto_start` is needed because PAM's session phase runs before the user
   systemd manager starts, so the daemon is not yet up to receive the password.
   It may leave a third daemon around; if that misbehaves, mask
   gnome-keyring-daemon.socket rather than dropping `auto_start`.

Ruled out: `nopasswdlogin` (joel is in the group, but nothing in /etc/pam.d
references it -- vestigial, probably from sddm; a password *is* collected at
login, so there is something for PAM to pass along).

Not the same bug as [[dots-cdb6]], despite both being auth prompts: that one is
polkit, this one is PAM.
